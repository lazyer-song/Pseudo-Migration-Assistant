# 伪迁移助手 — 设计方案（v0.1 / 计划阶段）

> 名字的由来：它不是真的"移动"文件，而是在 C 盘原位置留一个目录联接（Junction），
> 数据实际躺在别的盘上——程序访问的还是老路径，所以叫"伪"迁移。

> 目标：把 `C:\` 下的大体积目录**安全地**搬到 `D:\`（或 `E:\`），原位置留一个目录联接（Junction），
> 让程序完全无感地继续读写。要求：可回滚、可审计、不出"半迁移"状态。
>
> **交付形态：单个 `.exe`，免安装绿色版**——双击即用、可放 U 盘、不依赖任何运行时、不留安装痕迹。
>
> **技术栈：C# / .NET 8 + NativeAOT + 原生 Win32 对话框**——单 exe 约 10 MB，零解压、秒启动。
>
> 环境实测：`C:` 257.6 GB / 剩 106 GB（NTFS, Fixed），`D:` 931.5 GB / 剩 567 GB，`E:` 669.6 GB / 剩 496 GB。

---

## 0. 一句话结论

思路完全可行，但**"先复制、再把原目录改名成 `.bakup`"还不够**，因为它没定义清楚：
**什么时候可以删 `.bak`、删了之后还能不能回滚、断电了怎么判定现场**。

正确模型是**五步提交 + 三个可回滚窗口**：

```
复制 → 校验 → 原子改名 → 建 Junction → 探针验证 →（宽限期后）释放备份
 ①      ②        ③            ④           ⑤              ⑥
        └──────── 全部可零成本回滚 ────────┘        └── 靠目标盘副本回滚 ──┘
```

**真正的"备份"是目标盘上那份已校验的副本，不是 C 盘的 `.bak`。**
C 盘的 `.bak` 唯一价值是让回滚从"几分钟"变成"几毫秒"。想清楚这一点，策略就清晰了。

## 1. 技术底座：为什么是 Junction

| 方式 | 建链权限 | 能否指向文件 | 能否指向网络 | 程序兼容性 | 结论 |
|---|---|---|---|---|---|
| **目录联接 Junction** (`mklink /J`) | **不需要管理员** | 否（只能目录） | 否 | 最好，绝大多数程序无感 | ✅ 首选 |
| 目录符号链接 (`mklink /D`) | 需管理员或开发者模式 | 是 | 是 | 较好，少数老程序/服务会出问题 | 仅当目标必须是 UNC 时用 |
| 硬链接 (`mklink /H`) | 不需要 | 是（文件级） | 否 | — | ❌ 不能链目录，且不能跨卷 |

**Junction 的几个关键事实（决定了设计细节）：**

1. Junction 是 NTFS 重解析点（`IO_REPARSE_TAG_MOUNT_POINT`），由本地文件系统在**对象管理器层**解析，
   应用层拿到的仍是 `C:\...` 原路径，所以配置里写死的绝对路径不受影响。
2. 目标**必须是本地卷上的目录**，不能是 UNC 路径。→ 目标盘只能是固定磁盘。
3. 目标目录必须**先存在**才能建链。
4. 目标路径以 `\??\C:\...` 形式存盘，**盘符一变就断**（后面有缓解方案）。
5. 删除 Junction（`rmdir` / `Directory.Delete`）**只删链接，不删目标内容**——这是安全的；
   但 `robocopy /MIR`、某些递归删除工具**会穿透**它去删目标内容——这是危险的，必须 `/XJ`。
6. 内容访问受**目标目录的 ACL** 约束；链接本身的安全描述符只影响对链接对象的操作。

**跨卷"移动"无法原子完成**：`MoveFileEx` 带 `MOVEFILE_COPY_ALLOWED` 对目录跨卷会直接失败，
所以只能自己做"复制 + 换位"。这也正是需要状态机的原因。

## 2. 核心流程（详细版）

### 2.1 阶段分解

```
[0] 预检 Preflight         只读，不改任何东西
[1] 复制 COPYING           C:\...\Foo → D:\Migrated\C\...\Foo.__incoming__
[2] 校验 VERIFIED          元数据比对 + 抽样/全量哈希
[3] 就位               D:\...\Foo.__incoming__ → D:\...\Foo        （同卷改名，原子）
[4] 让位               C:\...\Foo → C:\...\Foo.__bak_20261020_1646__
[5] 建链               C:\...\Foo → Junction → D:\...\Foo
[6] 探针 PROBED            通过 C: 路径写一个探针文件，确认它出现在 D: 上，再删掉
[7] 保留期 RETENTION       .bak 保留 24h（可配），期间一键秒回
[8] 释放 CLEANED           删除 .bak（此刻 C 盘空间才真正回来）
```

**为什么先复制到 `.__incoming__` 而不是直接复制到最终目录名？**
避免"看起来完整、其实拷了一半"的目录被程序误用；改名是同卷元数据操作，微秒级。

**为什么 [4] 和 [5] 之间是危险窗口？** 见 §6.1，这是整个方案最需要工程处理的地方。

### 2.2 状态机：只有 4 个时刻必须落盘

内存里的细粒度状态：

```
COPYING → COPIED → VERIFIED → SWAPPING → LINKED → PROBED → RELEASED
```

但**只有 4 个时刻必须写进目标端 manifest**（§8.4），因为它们是"断电后无法从现场推断"的：

| 落盘时机 | op | 为什么必须 |
|---|---|---|
| 开始复制前 | `plan` | 知道 D 盘那个 `.__incoming__` 属于谁，可安全清理 |
| **改名之前** | `swapping` | 唯一的"半途"状态：源已改走、链接未建。不写这条，断电后无法区分"没开始"和"卡在中间" |
| 探针通过后 | `linked` | 进入"待释放"，可回滚可释放 |
| 释放 / 回滚完成 | `released` / `rolledback` | 终态 |

**写前记录（WAL）**：先写 `swapping` 再改名，保证任何时刻 manifest 都不比文件系统旧。

崩溃恢复矩阵（启动时：读 manifest + 看现场）：

| manifest 最后状态 | 现场 | 判定 | 动作 |
|---|---|---|---|
| `plan` | 源是真目录 | 复制未开始或未完成 | 删 `.__incoming__`，提示"已清理 1 个未完成迁移" |
| `swapping` | 源是 Junction | 换位完成，只差没写 `linked` | 补写 `linked`，直接进待释放 |
| `swapping` | 源缺失 + `.bak` 在 | 改名后、建链前崩溃 | `.bak` 改回原名，补写 `rolledback` |
| `swapping` | 源是真目录 + `.bak` 在 | 程序重建了目录 | **不自动处理**，列差异让人工决定 |
| `linked` | 正常 | 完成 | 进待释放列表 |

### 2.3 参考命令序列（可直接验证的最小实现）

```powershell
# 0) 体检（只读）
$src = 'C:\Users\me\AppData\Local\SomeApp'
$dst = 'D:\Migrated\C\Users\me\AppData\Local\SomeApp'
robocopy $src $dst /L /E /XJ /NFL /NDL /NJH /NP     # 干跑，只列不拷

# 1) 复制（多线程、跳过重解析点、失败重试1次）
robocopy $src "$dst.__incoming__" /E /COPY:DAT /DCOPY:DAT /XJ /R:1 /W:1 /MT:16 /NP /LOG:migrate.log

# 2) 校验（此处伪代码，见 §5 分级策略）
# 3) 就位
Rename-Item "$dst.__incoming__" (Split-Path $dst -Leaf)

# 4) 让位
Rename-Item $src "$src.__bak_$(Get-Date -f yyyyMMdd_HHmmss)"

# 5) 建链（不需要管理员）
New-Item -ItemType Junction -Path $src -Target $dst | Out-Null

# 6) 探针
'probe' | Set-Content "$src\__probe__.tmp"
if (-not (Test-Path "$dst\__probe__.tmp")) { throw 'Junction 未生效，立即回滚' }
Remove-Item "$src\__probe__.tmp"

# 7) 保留期后再删 .bak（见 §3.3）
```

## 3. 回滚设计（重点回答你的问题）

### 3.1 三个窗口期，三种回滚成本

| 卡在哪一步 | C 盘现场 | 回滚动作 | 耗时 | 数据风险 |
|---|---|---|---|---|
| ① 复制中 / 复制完未校验 | 原目录**完好未动** | 删掉 `D:\.__incoming__` | 秒级 | **零** |
| ② 已建 Junction，`.bak` 还在 | 一个链接 + 一个 `.bak` | 删链接 → `.bak` 改回原名 | **毫秒级** | **零** |
| ③ `.bak` 已删除 | 只剩 Junctions | 删链接 → 从 D: 复制回来 → 校验 | 分钟级（= 一次复制） | **零**（副本仍在） |

**结论：唯一不可逆的点是 [8] 删除 `.bak`；在此之前，一切都能秒回。**
所以整个设计围绕一件事：**把"删除 `.bak`"变成一个显式、可延迟、可审计的动作**。

### 3.2 关键认知：保留 `.bak` 不会让 C 盘更满

`.bak` 就是原来那个目录改名而来，**它本来就在占用 C 盘**。保留它不增加任何额外占用，
只是**延迟**了空间的释放。真正增加的占用是 D 盘上多了一份副本（峰值总占用 ≈ 2×）。

所以"先保留 24 小时再说"几乎没有代价，只是 C 盘的 106 GB 暂时没变多。

### 3.3 备份保留策略

| 模式 | 行为 | 适用 |
|---|---|---|
| **`ask`（默认）** | 保留到用户确认；每次启动顶部提示"N 个待释放，共 XX GB" | 绝大多数场景 |
| `auto:7d` | 启动时惰性清理超过 7 天的 | 不想每次被问，但也不当场删 |
| `now` | 探针通过即删 | 缓存类目录（npm、Gradle、缩略图） |
| `forever` | 永不清理 | 只在测试流程时用 |

> 注意：**不注册计划任务**（见 §10.5）。所谓"7 天"是在**下次启动时**判定，不是后台定时。
> 这也让"纯 exe、即开即关"的定位自洽：没有常驻进程，没有系统里看不见的定时器。

**默认 `ask` 的理由**：迁移出错最常见的暴露时机是"下次启动程序"，而那时候用户正好会再打开这个工具。

### 3.4 为什么不是"只复制 + 改名 .bak"

因为你最终还是要删掉 `.bak` 才能省空间，那一刻你就进入了"只能靠目标盘副本回滚"的状态。
与其把这件事藏起来，不如**显式建模**：`.bak` 是"快速回滚窗口"，目标盘副本是"最终真相"。

另外，单纯"复制 + 改 `.bak` 而不建链"，程序下次启动会**在 C 盘重建一个空目录**，
于是新旧数据分裂（split brain），比不迁更糟。**必须建链，且必须验证链生效。**

### 3.5 三种收尾模型：谁来决定删副本

迁移在**探针通过的那一刻**就已经完成了——链接已生效，程序已在用新位置。
剩下唯一的动作是"删不删 C 盘那份副本"。

| 模型 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **A 两段式（询问）** | 迁完保留 `.bak`，用户当场或下次启动决定是否删 | 秒级回滚窗口最长，可先试用几天 | 用户可能忘，空间迟迟不释放 |
| **B 一次性（自动删）** | 探针通过后立即删 `.bak`，只留目标端记录 | 流程干净，空间立刻回收 | 删源不可逆，大目录删除慢且可能失败，出问题只能慢速复原 |
| **C 混合（推荐）** | 默认 A；缓存类目录可勾选"迁完即删"，或当场确认 | 兼顾 | 多一个选项 |

**为什么推荐 C（默认 A），四条理由：**

1. **校验只能证明"复制正确"，证明不了"程序兼容"。** Junction 对 99% 的程序透明，
   但剩下那 1%（用 `GetFinalPathNameByHandle` 做身份校验的、反作弊、某些安装器/更新器）
   只有**下次启动程序**时才暴露。
2. **删源之后复原需要 C 盘有空间。** 你迁走正是因为 C 盘满；删了 `.bak` 之后 C 盘又被塞满时，
   复原可能**因空间不足而失败**。保留 `.bak` 时复原只是改名，零空间需求。
3. **保留期是唯一"两份数据落在不同物理盘"的窗口**，顺带防一手 D 盘故障。
4. **删源不是原子操作**：十万文件的删除要几分钟，中途遇到占用就失败，
   留下删了一半的 `.bak`，比"完整保留"更难判断。

**所以把语义拆开：**

```
迁移 = 复制 → 校验 → 换位 → 建链 → 探针      ← 到这儿就是"完成"
收尾 = 删除 .bak                              ← 独立动作，用户决定
```

UI 上不要说"未完成"，要说"**已迁移，待释放 12.4 GB**"。

**B 模型不禁止，只是不该默认。** 缓存类目录（npm、Gradle、缩略图）删了也无所谓，
给个"迁完即删"的勾选；普通程序目录默认保留。

**"不存状态"也能实现"下次提醒"**：不需要任何本地状态文件——启动时读取目标端登记表（见 §8.4），
再对每条记录 `stat` 一次它对应的 `.bak` 是否存在即可。`.bak` 目录**本身就是状态**。

### 3.6 复原（反向流程）

入口两个：`c2d rollback <路径>` 与结果页的"立即回滚"。

```
[1] 预检：源路径当前必须是 Junction；目标目录存在且可读
[2] .bak 还在  → 删链接 → .bak 改名回原位              （秒级，零空间需求）
[3] .bak 已删  → 删链接 → 检查 C 盘剩余 ≥ 大小 × 1.05
               → 复制回 C → 校验 → 删目标副本 → 删记录   （分钟级，需空间）
[4] 冲突：C 路径上已出现"真目录"（程序重建过）→ 不覆盖，列差异让用户合并
```

**复原就是"反向的一次迁移"，同样要预检、同样要校验、同样不能裸删。**

## 4. 预检（Preflight）检查清单

> 原则：**能在预检阶段拒绝的，绝不留到执行阶段才发现。**

### 4.1 路径与身份

- [ ] 源存在、是目录、**不是**重解析点（若是 → 显示当前指向，提供"改指向 / 解除"而非再套一层）
- [ ] 源不是卷根、不是 `C:\Users\<me>` 本身、不是被系统"位置"功能重定向过的已知文件夹
- [ ] 路径规范化：大小写、尾随空格/点、8.3 短名、`\\?\` 前缀（用 `GetFinalPathNameByHandle` 取**真实**路径比较，而非字符串比较）
- [ ] 源与目标**互不包含**（`C:\a` → `C:\a\b` 会无限递归；必须规范化后判断前缀）
- [ ] 目标不在源内部，源不在目标内部
- [ ] 目标最终路径不存在，或存在但为空（可复用）

### 4.2 卷与容量

- [ ] 目标卷 `DriveType == Fixed`（**拒绝** Removable / Network / CDRom）
- [ ] 目标文件系统为 NTFS / ReFS（exFAT/FAT32 强警告：**无 ACL、单文件 4 GB 上限、无 ADS**）
- [ ] 目标剩余 ≥ 源大小 × 1.10 + 2 GB
- [ ] 复制过程中持续监控剩余空间，低于 1 GB 立即中止
- [ ] 目标卷 BitLocker 状态 vs 源卷（源加密、目标不加密 → **敏感数据裸奔**警告）

### 4.3 内容风险扫描

- [ ] 源内是否存在重解析点（junction / symlink / OneDrive 占位符 / WSL / 去重）→ **默认中止并列出**
- [ ] 是否存在 EFS 加密文件、稀疏文件、硬链接、备用数据流（ADS / Zone.Identifier）
- [ ] 是否存在 >260 字符的长路径（计数并提示）
- [ ] 是否存在只读 / 系统 / 隐藏属性的关键文件
- [ ] 文件总数、总字节、最大文件（用于 ETA 与进度基数）

### 4.4 占用检测：什么才算"被占用"

**两件事不要混：**

| 阶段 | 关心什么 | 后果 |
|---|---|---|
| 复制 | 有没有人**正在写** | 可能拷到"半截"内容 → 校验会发现并中止 |
| 换位（改名） | 有没有人**打开着**，哪怕只读 | 改名直接失败 |

**为什么只读也挡得住改名？** 改名一个目录，系统要同步改掉目录里所有已打开文件的路径，
所以要求每个打开句柄都带 `FILE_SHARE_DELETE`。而绝大多数程序打开文件时只给
`FILE_SHARE_READ`（甚至不给共享），于是改名报 `ERROR_ACCESS_DENIED`——
就是那句"文件夹或文件已在另一个程序中打开"。

**资源管理器打开文件夹算不算？** **基本不算。** 它显示目录时持的是变更通知句柄
（`ReadDirectoryChangesW`），带 `FILE_SHARE_DELETE`，不会阻断改名。但下面这些**会**：

- 你在里面**选中了**文件，预览窗格 / 缩略图去打开它（PDF、Office、视频最常见）
- 某个进程的**当前工作目录**在这个文件夹里（cmd / PowerShell `cd` 进去过，这个最容易被忽略）
- 文件被程序打开：Office、编辑器、播放器、数据库、日志查看器
- 杀软正在扫描、索引服务正在建索引
- 文件夹是某个共享的根，或被某个服务当作数据目录
- 文件被内存映射（DLL 已加载、SQLite 的 WAL/SHM）

**别靠枚举进程去猜。** 两条可靠判定：

1. **Restart Manager**：`RmRegisterResources` 喂文件列表，`RmGetList` 拿占用进程。
   缺点：只能看到"愿意被枚举"的应用，杀软和服务常常漏。
2. **试改名（推荐，ground truth）**：`Foo` → `Foo.__probe_<guid>__`，立刻改回。
   2 毫秒，能 100% 回答"这次换位会不会成功"。**它做的就是你真正要做的那件事。**

实践用两段式：**预检时试一次**（失败就早退，别浪费 30 分钟复制），**换位前再试一次**（最终闸门）。

> 复制期间源文件被改了怎么办？不需要额外机制——校验阶段源与目标必然不一致，自然中止。
> **校验本身就是并发修改的检测器。**

权限相关：

- [ ] 当前用户能否读取全部内容（不能 → 提示需要 `/B` 备份模式 + 提权）
- [ ] 目标父目录可写
- [ ] 目标路径 ACL：**若源被 SYSTEM/服务使用，目标必须禁止普通用户写入**（见 §7.2）

### 4.5 生态影响

- [ ] 是否在 OneDrive / Dropbox / 坚果云 等同步根内 → 强警告（同步引擎可能不跟随 Junction，甚至删除链接重建目录）
- [ ] 是否被 Windows Search 索引（迁移后该目录搜索可能失效）
- [ ] 是否被备份软件（Acronis / 群晖 Active Backup / Windows 备份）覆盖
- [ ] 是否存在上次未完成的 `.bak` / `.__incoming__` 残留 → 先走恢复流程

## 5. 校验策略（正确性 vs 性能的平衡）

三级可选，默认 L2：

| 级别 | 方法 | 成本 | 能发现的问题 |
|---|---|---|---|
| **L0** | robocopy 退出码 + 文件数 + 总字节 | ≈0 | 大规模丢失 |
| **L1** | 逐文件 `大小 + 最后写入时间` 比对 | 极低（复制时顺手统计） | 截断、漏拷、时间戳错乱 |
| **L2（默认）** | L1 + 抽样哈希：全部 <4 MB 的文件 + 每个大文件首尾各 1 MB + 随机 10% | ≈10–20% 额外 | 静默损坏、位翻转 |
| **L3** | 全量 SHA-256 双向比对 | ≈ 2× 数据量的读 | 一切 |

- L2 的抽样哈希用 **xxHash128 / BLAKE3**（10+ GB/s，非加密强度，查错足够）；
- L3 用 SHA-256（有 SHA-NI 硬件加速，NVMe 上约 1–2 GB/s/端）；
- 50 GB 目录：复制约 1–2 分钟，L2 校验约 20 秒，L3 约 2–3 分钟。

**校验不通过的唯一正确处理：中止，删掉 `D:\.__incoming__`，源保持在原位，报告哪几个文件不一致。**
不要"重试几次就算了"，也不要带着不一致去建链。

## 6. 失败模式与恢复矩阵

### 6.1 路径"空窗期"与数据分裂（最容易被忽略的坑）

[4] 改名完成到 [5] 建链完成之间，`C:\...\Foo` **不存在**。如果此刻有程序在跑：

- 轻则报错（"找不到路径"）；
- **重则程序自动 `CreateDirectory` 重建一个空目录** → 建链失败（已存在）→ 老数据在 `.bak`、新数据在新目录，
  形成 **split brain**，用户看到的是"配置丢了"。

对策：
1. 预检阶段检测到占用进程 → **默认拒绝执行**，让用户先关程序；
2. [4][5] 之间只做两次元数据操作，目标 <50 ms；
3. 建链失败时检查该路径是否被重建：若新生成了目录，**先把新文件合并进目标副本，再重试**，而不是直接覆盖；
4. 提供 `--force-close`（可选）用 Restart Manager 优雅关闭相关进程（要二次确认）。

### 6.2 崩溃 / 断电后的现场判定

启动时扫描所有非终态 journal 记录，按下表自动给出动作：

| C 盘现场 | D 盘现场 | 判定 | 动作 |
|---|---|---|---|
| 真目录 | `.__incoming__` | 未提交 | 删 `.__incoming__`，回到起点 |
| 真目录 | 完整 `Foo` | 已复制未换位 | 删 D 副本（或保留供重试） |
| `.bak_*` | 完整 `Foo` | 换位一半 | `.bak` 改回原名，回到起点 |
| Junction | 完整 `Foo` + `.bak_*` | 已换位未清理 | 标记 PROBED，进入保留期 |
| Junction | 目标不存在 | 目标盘离线 / 盘符变了 | 修复指向，或回滚 |
| **真目录** | 完整 `Foo` + 有 Junction 记录 | **split brain** | **禁止自动处理**，列出双方差异，人工合并 |
| 无目录 | 完整 `Foo` | 最坏情况 | 从 D 复制回来重建（数据仍在） |

### 6.3 运行期故障

| 故障 | 表现 | 对策 |
|---|---|---|
| D 盘拔掉 / 掉线 | 程序访问 `C:\...\Foo` 报"找不到路径" | 使用须知里写死"目标盘必须常驻"；`doctor` 开机自检 |
| 盘符变化（D→E） | 所有 Junction 集体失效 | **Volume GUID Junction**（见 §9.4）或 `doctor` 一键批量重指向 |
| 程序卸载时删掉了 Junction | D 盘数据成孤儿 | `doctor` 报告"目标有数据但源无链接"，可一键恢复链接 |
| 程序重建真目录 | split brain | `doctor` 对比 manifest 检测并告警 |
| 目标盘满 | 复制中断 | 源未动，零成本回滚 |
| 杀软拦截 | 复制/建链失败 | 识别错误码并给出明确指引，不要笼统报"未知错误" |

## 7. 安全设计

### 7.1 最小权限

**建 Junction 不需要管理员**，所以整个工具**默认不提权**（`asInvoker`）。
只有两种情况按需提权并**明确告知原因**：

- 读取当前用户无权访问的文件（`/B` 备份语义，需 `SeBackupPrivilege`）；
- 写入受保护的目标路径。

### 7.2 提权攻击面（很重要）

Junction 是 Windows 上经典的**符号链接/联接攻击**载体。规则：

> **绝不要把一个高权限进程（SYSTEM / 服务 / 管理员自启程序）使用的目录，指向一个低权限用户可写的位置。**

否则普通用户可以往目标目录里塞文件，被高权限进程当作可信内容加载 → 本地提权。

实现上：预检阶段读取目标路径的 DACL，如果源目录的 ACL 显示"仅管理员/SYSTEM 可写"，
而目标路径允许 `Users` 写入 → **拒绝，或要求把目标目录 ACL 收紧到同等水平**。

### 7.3 数据保护

- 默认复制 DACL（`/COPY:DATS` 或 `icacls /save`），并在校验阶段抽样比对 ACL；
- 目标为非 NTFS → 明确告知"权限与加密属性将丢失，多用户机器上等于对所有人开放"；
- 源卷开了 BitLocker、目标卷没开 → 警告（浏览器配置里有 Cookie/密码库）；
- 日志只记路径与统计，**不记文件内容**；不上传、不联网、无遥测。

### 7.4 防误删（几个具体的坑）

1. **只删自己创建的 `.bak`**：`.bak` 目录里放一个 `.c2d-owner.json`（含 journal id + 源路径哈希），
   删除前校验标记，防止误删用户自己命名的同名目录。
2. 删除前**再次确认**该目录不是 Junction（`Directory.Delete(recursive:true)` 对 Junction 只删链接，
   但如果路径被替换成真目录就会真删内容）。
3. 所有删除操作走"先改名到隔离区 → 再删"，或至少要求二次确认。
4. **TOCTOU 防护**：复制完成后重新读取源目录的 `VolumeSerialNumber + FileId`，确认还是同一个对象，
   否则重来（防止复制期间目录被替换）。

## 8. 交互设计

### 8.1 唯一入口：GUI

**不做 CLI。** 程序只有一种形态：双击打开的主窗口，所有操作都在窗口里完成。

```
主窗口
├── 顶部：选择文件夹迁移…
├── 中部：待释放列表（常驻，见 §8.6）
├── 底部：已迁移统计
└── 迁移中：整块切换为任务视图（见 §8.2）
```

理由：这个工具的使用者是"想把 C 盘腾出来的普通用户"，不是脚本。少一套入口 = 少一半测试面。

代价：不能脚本化做端到端测试。对策是编译时保留一个**不对外**的 `/selftest <目录>` 入口
（发布版用编译常量裁掉），只用于自动化验证"复制 → 校验 → 建链 → 回滚"整条链路。

> **没有任何操作会遍历整个磁盘。** 范围要么是用户选的那个目录，要么是清单里记的那几条路径。

### 8.2 迁移进度：显示到"正在复制哪个文件"

```
┌──────────────────────────────────────────────────────────────┐
│  正在迁移   C:\Users\me\AppData\Local\SomeApp              │
│                                                               │
│  ① 检查 ── ② 复制 ── ③ 校验 ── ④ 切换 ── ⑤ 验证              │
│              ●                                                │
│                                                               │
│  ████████████████████░░░░░░░░░░  68%                          │
│  8.4 / 12.4 GB · 42 MB/s · 剩余约 1 分 32 秒                  │
│                                                               │
│  正在复制  …\Cache\data\00042.bin        12,048 / 38,201      │
│                                                               │
│  [ 取消 ]                                        [ 详情 ▾ ]   │
└──────────────────────────────────────────────────────────────┘
```

五行信息，缺一不可：

| 行 | 内容 | 更新频率 |
|---|---|---|
| 阶段条 | 检查 / 复制 / 校验 / 切换 / 验证 | 阶段变化时 |
| 总进度 | **按字节**的百分比 | 10 Hz |
| 速率与 ETA | 滑动窗口平均，不用瞬时值 | 1 Hz |
| 当前文件 | 完整路径，过长时省略中间 | 10 Hz |
| 计数 | 已完成 / 总文件数 | 10 Hz |

**为什么按字节而不是按文件数**：38,201 个文件里可能有 3 个占 90% 的体积，按文件数会卡在 99% 很久。

**每阶段的进度基准：**

| 阶段 | 基准 | 说明 |
|---|---|---|
| ① 检查 | 不确定态（跑马灯） | 扫目录、算大小、试改名、查占用 |
| ② 复制 | 字节 | 主阶段，耗时最长 |
| ③ 校验 | 已校验文件数 | L2 抽样时按文件数计 |
| ④ 切换 | 瞬间 | 两次 rename + 建链，<100 ms，直接跳满 |
| ⑤ 验证 | 瞬间 | 探针写入并读回 |

**线程模型**（决定窗口会不会"未响应"）：

```
UI 线程          只做绘制，绝不碰文件
   ▲
   │ WM_TIMER 100 ms 拉一次快照
   │
工作线程池       复制 / 校验，只更新无锁的 ProgressState
```

- 工作线程**不直接调 UI**，只 `Interlocked` 累加计数器；
- UI 每 100 ms 读一次快照重绘；
- 即使磁盘卡顿，窗口依然可拖动、取消按钮依然可点。

**取消**：`CopyFileEx` 的进度回调每个数据块都会被调用，回调返回 `PROGRESS_CANCEL`
即可在 1 MB 内停下；停下后自动删 `.__incoming__`，源目录全程没动过。

**并行的取舍**：小文件多时 8 线程能快 2–3 倍，但"当前文件"会变成 8 个。
方案：**≥32 MB 的大文件串行复制并显示名字；小文件并行，只显示最近一个 + 聚合计数。**

**其它交互原则：**

- 首次使用强制干跑一次，让用户先看到"到底会发生什么"；
- 危险动作（删 `.bak`、强制关闭进程）二次确认 + 写明后果，不只弹"确定吗"；
- 完成后给 **10 秒撤销**（有 `.bak` 时回滚是毫秒级的）；
- 批量迁移一个一个提交，失败即停。

### 8.3 右键菜单（可选）

`HKCU\Software\Classes\Directory\shell\C2DMigrate`，注册一个"迁移到其他盘…"，
调用 `c2d run "%1"` 的 GUI 模式。仅当前用户，不需要管理员。

### 8.4 目标端登记表（唯一的持久化）

**位置固定**：`<目标盘>:\Migrated\.c2d\manifest.jsonl`

位置固定带来一个关键好处：**启动时不需要扫描**。枚举固定卷（一般 3 个），逐个
`Test-Path X:\Migrated\.c2d\manifest.jsonl` —— **3 次 stat，微秒级**。

这也是为什么目标路径模板要定成 `<盘>:\Migrated\...` 的镜像结构：它同时解决了"清单在哪"。

**格式：事件日志，追加写，按 `id` 折叠。**

```jsonl
{"v":1,"id":"m_20261020_1714_a1","op":"plan","src":"C:\\Users\\me\\...\\SomeApp","dst":"D:\\Migrated\\C\\Users\\me\\...\\SomeApp","bytes":13314398617,"files":38201,"at":"2026-10-20T17:14:03+08:00"}
{"v":1,"id":"m_20261020_1714_a1","op":"linked","bak":"C:\\Users\\me\\...\\SomeApp.__bak20261020_1714__","at":"2026-10-20T17:18:22+08:00"}
{"v":1,"id":"m_20261020_1714_a1","op":"released","at":"2026-10-23T09:02:11+08:00"}
```

`op` 取值：`plan`（开始）→ `linked`（链接生效，副本待释放）→ `released` / `rolledback`（终态）。
读取时按 `id` 取最后一条 = 当前状态。

**为什么用事件日志而不是"改一行"**：追加写永远不重写文件，断电最多丢最后一行，前面全部完好；
而改写文件中间一行，一次断电就可能把整份清单写坏。

**启动时怎么算出"待释放"：**

1. 枚举固定卷，找到所有 `\Migrated\.c2d\manifest.jsonl`
2. 逐行解析，按 `id` 折叠出当前状态
3. 只取 `op == "linked"` 的条目
4. 对每条 `stat(bak)`：存在 → 待释放；不存在 → 用户手工删过，补一条 `released`
5. 汇总大小与条数

成本：3 次存在性检查 + 解析几十 KB + N 次 stat（N 通常 < 50）。**毫秒级，可忽略。**

四个用途：复原依据、待释放索引、审计统计、冲突检测（同一目标被两个源指向）。

---

### 8.5 记录损坏：报错，不扫描

**红线：任何情况下不做全盘遍历。**
所有操作的范围必须由"用户选择的目录"或"清单里的具体路径"限定——这是轻量工具和"把电脑搞卡"的分界线。

| 故障 | 处理 |
|---|---|
| 某一行 JSON 损坏 | 跳过该行，其余照常；界面标一条"1 条记录无法解析" |
| 整个文件读不了（权限 / 损坏 / 被占用） | **明确报错**，不猜、不扫，提供"手动指定原路径" |
| `.c2d` 目录被删 | 视为"无记录"：已建好的链接照常工作，但**无法自动复原** |
| 目标盘不在线 | 该盘条目全部标灰，不报错、不重试 |

**手动复原（唯一的兜底，只在前三种情况出现）：**

```
报错 → 用户点"手动复原" → 选择一个 C 盘目录 →
   它是 Junction 且指向该目标  → 直接回滚（秒级）
   它是真目录（数据还在）      → 列出差异，让用户决定合并还是放弃
   不存在                      → 从目标复制回去（分钟级，需空间）
```

**明确不做"扫描重建"**：全盘遍历几十万目录，机械盘上要几分钟，还会把系统盘 I/O 打满。
宁可让用户点两下，也不让工具自作主张跑一次全盘扫描。

## 9. 性能设计

### 9.1 复制

- `robocopy /E /COPY:DAT /DCOPY:DAT /XJ /R:1 /W:1 /MT:16 /NP /NFL /NDL`
- 大文件追加 `/J`（无缓冲 I/O，绕过缓存，减少内存抖动）
- `/MT` 对**大量小文件**有效（16–32），对单个大文件无效；`/MT` 与 `/IPG` 互斥
- 目标若是机械盘 / USB，加 `/IPG:50` 限速，避免把系统拖死
- **Windows Defender 实时扫描是最大变量**：复制缓存类目录时临时排除源+目标（操作后恢复），
  可提升 2–5 倍。这个功能要显式开关 + 明确提示，默认关。

### 9.2 校验

见 §5。要点：**L2 默认**，抽样而不是全量；哈希用硬件加速或非加密哈希。

### 9.3 预扫描

几十万小文件的目录，光是"算大小"就可能几十秒。用
`FindFirstFileEx(FIND_FIRST_EX_LARGE_FETCH)` + 多线程遍历，或直接解析 `robocopy /L` 的输出。

### 9.4 抗盘符变化（进阶）

创建 Junction 时把目标写成 **Volume GUID 路径**：

```
\\?\Volume{3f2a...-...}\Migrated\C\Users\me\AppData\Local\SomeApp
```

这样即使 D 盘变成 E 盘，链接依然有效。代价是可读性差、部分工具显示异常。
建议做成选项 `--stable-link`，默认关闭，**等实测通过后再作为高级用户的推荐项**。

### 9.5 预期吞吐（参考）

| 场景 | 预期 |
|---|---|
| NVMe → NVMe，大文件 | 1.5–3 GB/s（受限于源盘读） |
| 大量小文件（10 万+） | 3k–15k 文件/秒（`/MT:16`） |
| L2 校验 | 额外 +10–20% 时间 |
| L3 全量 SHA-256 | 额外 +100%（约等于再读一遍双端） |

## 10. 交付形态：单文件便携 exe（硬约束）

最终产物 = **一个 `.exe`，免安装、绿色、拷贝即用**。这条约束会反向影响技术选型，先把它拆开。

### 10.1 它实际意味着 5 件事

1. **不能依赖外部运行时**（目标机器可能没装 .NET / VC++ 运行库 / Python）→ 自包含或 AOT。
2. **不能有外部资源文件**（图标、配置、DLL、语言包）→ 全部内嵌为嵌入资源。
3. **不能有安装/卸载流程** → 不装服务、不建计划任务、不写 HKLM；系统集成必须显式且可逆。
4. **运行状态不能污染 exe 目录**（用户可能放 U 盘或只读目录）→ 状态写 `%LOCALAPPDATA%`。
5. **体积与启动要体面** → 双击到界面 < 1 秒，体积控制在 20 MB 以内。

### 10.2 体积 / 启动预算

| 方案 | 体积 | 冷启动 | 启动时解压 | AV 误报 | 评价 |
|---|---|---|---|---|---|
| **C# .NET 8 + NativeAOT** | **6–15 MB** | **~20–50 ms** | **否** | 低 | ✅ 首选 |
| C# 自包含单文件（trimmed） | 25–40 MB | 200–600 ms | 是（解到 `%TEMP%\.net`） | **中** | 备选 |
| C# 自包含单文件（未 trim） | 60–80 MB | 300–800 ms | 是 | 中 | 不推荐 |
| **Go** | 6–12 MB | ~15 ms | 否 | 低 | ✅ 备选（GUI 更省事） |
| Rust | 1–4 MB | ~5 ms | 否 | 低 | 体积最优，开发慢 |
| Python + PyInstaller | 15–40 MB | 1–3 s | 是 | **高** | ❌ 排除 |
| Electron / Tauri | 80 MB+ / 3–8 MB | 慢 / 快 | — | — | ❌（Tauri 依赖 WebView2） |

> 关键：`.NET` 的 `PublishSingleFile` 若含原生库，**首次运行会解压到 `%TEMP%\.net\<hash>\`**。
> 这既是杀软误报的主要来源，也是"绿色软件"体验的破坏者（临时目录留垃圾、被杀软拦截）。
> **NativeAOT 不产生任何解压**，输出就是原生单 exe——这是它最大的优势。

### 10.3 发布配置

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>            <!-- 双击不弹黑框，见 10.6 -->
    <TargetFramework>net8.0-windows</TargetFramework>
    <RuntimeIdentifier>win-x64</RuntimeIdentifier>
    <PublishAot>true</PublishAot>              <!-- 天然单文件，无需 PublishSingleFile -->
    <SelfContained>true</SelfContained>
    <InvariantGlobalization>true</InvariantGlobalization>
    <UseSystemResourceKeys>true</UseSystemResourceKeys>
    <DebugType>none</DebugType>                <!-- 不产出 .pdb，保证真的只有一个文件 -->
    <ApplicationManifest>app.manifest</ApplicationManifest>
    <AssemblyName>c2d</AssemblyName>
    <Version>1.0.0</Version>
  </PropertyGroup>
</Project>
```

`app.manifest` 三件套：`asInvoker`（默认不提权）、`longPathAware`、`supportedOS`。
发布：`dotnet publish -r win-x64 -c Release`，产物目录里**只应有一个 `c2d.exe`**。

**AOT 的代价（提前认账）：**

- 不能用反射式 JSON → 用 `JsonSerializerContext` 源生成；
- 不能用 `System.Management`（WMI）→ 本方案本来就用 `DriveInfo` + `GetVolumeInformation`，无影响；
- **WinForms/WPF 在 AOT 下不可用** → 见 10.6 的 GUI 方案；
- 首次编译慢（几分钟），增量正常。

### 10.4 状态与配置放哪

| 内容 | 默认位置 | 说明 |
|---|---|---|
| journal / 历史 | `%LOCALAPPDATA%\C2D\journal\` | exe 被删/移动也不丢 |
| 日志 | `%LOCALAPPDATA%\C2D\logs\` | 滚动保留，默认只留 20 条任务 |
| 目标端冗余清单 | `D:\Migrated\.c2d\manifest.json` | C 盘重装也知道迁过什么 |
| 配置 | 内嵌默认值 | 可选读 exe 同级 `c2d.json`（存在才读） |
| **便携模式** | `<exe目录>\C2D.data\` | `--portable` 开启；目录不可写则自动回落 |

> 原则：**exe 目录默认可读可删**。删掉 exe 后残留只在 `%LOCALAPPDATA%`，一条 `c2d reset` 清干净。

### 10.5 零系统侵入

- **不装服务、不建计划任务、不写 HKLM**；
- 右键菜单是唯一需要注册表的集成 → 做成显式命令 `c2d shell install` / `c2d shell uninstall`，
  只写 `HKCU\Software\Classes\Directory\shell`，并记录 exe 路径；启动时检测"exe 被移动导致菜单失效"并提示重装；
- **用"启动时惰性清理"替代计划任务**：每次运行顺带检查过期 `.bak`（超保留期就清）。
  比注册计划任务优雅，也完全符合绿色定位；
- 单实例：`Local\C2D.SingleInstance` 互斥体 + journal 文件锁，防止两个窗口同时操作同一目录。

### 10.6 一个 exe，两种形态（双击 GUI / 命令行 CLI）

`OutputType=WinExe` 让双击**不弹黑色控制台窗**，直接进 GUI；同时启动时尝试
`AttachConsole(ATTACH_PARENT_PROCESS)` 挂到调用者控制台，于是从 PowerShell/CMD 运行时
`c2d run ...` 又能正常输出文本。

```
无参数 或 --gui  →  图形界面
有参数           →  命令行模式（输出到父控制台）
```

**GUI 不引入 WinForms/WPF**（AOT 不支持且体积暴涨），全部用原生控件：

| 需求 | Win32 方案 | 体积代价 |
|---|---|---|
| **主窗口 + 待释放列表** | `CreateWindowEx` + `SysListView32`（原生 ListView） | ≈0 |
| 选源目录 / 目标目录 | `IFileOpenDialog` + `FOS_PICKFOLDERS` | ≈0 |
| 进度显示 | 主窗口内嵌面板（原生 `msctls_progress32` + 自绘文字） | ≈0 |
| 确认 / 错误 | `TaskDialogIndirect`（原生外观，命令链接按钮） | ≈0 |
| 完成页 | `TaskDialog` + "立即回滚 / 立即释放 / 打开目标" | ≈0 |

**为什么必须有个主窗口**：你要的"待释放常驻显示"得有地方放——一个 `SysListView32` 加两个按钮
就是最省的原生方案。代价是要自己写窗口过程、处理 DPI 与字体（`WM_DPICHANGED`、
`SPI_GETNONCLIENTMETRICS`），工作量比纯对话框多，但换来**一打开就能看见欠了多少空间**。

```
┌─────────────────────────────────────────────┐
│  [ 选择文件夹迁移 ]           C2D 迁移工具   │
├─────────────────────────────────────────────┤
│  待释放 3 项 · 共 38.2 GB         [全部释放] │
│  SomeApp      12.4 GB   已保留 3 天          │
│  C:\Users\me\AppData\Local\SomeApp           │
│                       [回滚]  [释放空间]     │
│  ...                                         │
├─────────────────────────────────────────────┤
│  已迁移 12 项 · 累计释放 156 GB              │
└─────────────────────────────────────────────┘
```

这套组合是**纯正 Windows 原生外观**，比自绘 UI 更稳，体积几乎不增加。

### 10.7 升级、签名、分发

- **升级 = 覆盖 exe**。journal 带 `schemaVersion`，新版本必须能读旧记录（向前兼容）；
- **不做自我更新**（绿色工具自更新极易把自己搞坏），只提示有新版本；
- 未签名的 exe 首次运行会触发 **SmartScreen**（"更多信息 → 仍要运行"）。自己用无所谓；
  发给别人建议用 OV/EV 证书签名，否则大概率被当可疑程序；
- 内嵌版本资源（文件版本/产品名/图标），`c2d --version` 输出构建号与提交哈希，方便排查。

### 10.8 技术栈最终建议 + 关键 Win32 API

| 诉求 | 推荐 |
|---|---|
| 体积小、零解压、原生对话框 GUI | **C# .NET 8 + NativeAOT**（首选） |
| 想要更省事的原生窗口 GUI、不介意换语言 | **Go + `lxn/walk`**（单 exe 约 10–12 MB） |
| 只要命令行、极致体积 | Rust |

**关键 Win32 API（与语言无关）：**

- `CreateSymbolicLink`（`SYMBOLIC_LINK_FLAG_DIRECTORY | ALLOW_UNPRIVILEGED_CREATE`）或
  `DeviceIoControl(FSCTL_SET_REPARSE_POINT)` —— 建 Junction，不依赖 `cmd /c mklink`
- `DeviceIoControl(FSCTL_GET_REPARSE_POINT)` —— 读 Junction 真实目标
- `GetFinalPathNameByHandle` —— 路径规范化 / 判定包含关系
- `RmStartSession / RmRegisterResources / RmGetList` —— 占用进程枚举
- `CopyFileEx` / `CopyFile2` —— 带进度回调、原生处理稀疏/ADS/ACL 标志
- `GetVolumeInformation` / `GetDiskFreeSpaceEx` —— 卷信息与容量

> 注意：.NET 的 `Directory.Delete(path, recursive: true)` 对 Junction **只删链接**，
> 但不要依赖这个行为做安全保证——删除前永远显式判断 `FileAttributes.ReparsePoint`。

### 10.9 图标与版本资源（给设计的要求）

**要一个 `.ico`，多尺寸帧，不是把 PNG 改后缀。**

| 项 | 要求 |
|---|---|
| 容器 | 标准 ICO（多帧） |
| 必须包含尺寸 | 16、20、24、32、40、48、64、128、**256** |
| 位深 | 32-bit BGRA（带 alpha 通道） |
| 帧格式 | 16–48 用未压缩 BMP 帧；64–256 用 PNG 帧 |
| 色彩空间 | sRGB |
| 文件总大小 | < 200 KB |
| 背景 | 透明；不要自带白底方块（除非设计本身就是圆角底板） |
| 主体占比 | 画布内缩 8–10%，主体约占 80% |
| 16×16 可读性 | **必须单独检查**：线条 ≥ 1.5 px、不能有文字、轮廓清晰 |

尺寸各自用在哪：16 / 20 / 24 / 32 → 资源管理器小图标、任务栏、标题栏；
48 → 中等图标；256 → 大图标视图、设置应用、任务管理器。

**另外需要的两张图：**

- **1024×1024 PNG 源图**——我做多尺寸降采样，顺手按 Win11 视觉微调
- **256×256 PNG**——用于"关于"页和文档

**风格建议**：Win11 Fluent——圆角底板 + 单色符号，语义取"迁移 / 箭头 / 链接"；
避开细线、渐变细节和小字，16 px 下一定糊。

**版本资源**（我自动写入，文案你给）：

| 字段 | 示例 | 显示在哪 |
|---|---|---|
| ProductName | C2D 迁移工具 | 属性 → 详细信息、任务管理器 |
| FileDescription | C 盘目录迁移工具 | 任务管理器进程名 |
| CompanyName | — | 属性 → 详细信息 |
| LegalCopyright | © 2026 | 同上 |
| FileVersion | 1.0.0.0 | 同上、`--version` |

落地方式：文件命名 `app.ico` 放项目根，csproj 里 `<ApplicationIcon>app.ico</ApplicationIcon>`；
版本号走 `<Version>` / `<FileVersion>`。校验：`(Get-Item .\c2d.exe).VersionInfo`，
再用任意 ICO 查看器确认 9 个尺寸都在。

> 改图标必须重新编译——图标是编进 Win32 资源段的，不是外部文件。
> 资源管理器有图标缓存，改完可能要重启 explorer 才刷新。

## 11. MVP 里程碑

| 阶段 | 交付 | 估时 |
|---|---|---|
| **M0** | **先打通 AOT 单 exe 发布**（产物只有一个文件）+ `plan` 干跑 + 体检报告 + journal 骨架（不写盘） | 1 天 |
| **M1** | `run` 单目录：复制→L1 校验→换位→建链→探针→`rollback` | 2–3 天 |
| **M2** | L2/L3 校验、占用检测、重解析点扫描、`.bak` 生命周期、`cleanup` | 3–5 天 |
| **M3** | `scan` 候选发现、`doctor`、批量队列、原生对话框 GUI、右键菜单 | 3–5 天 |

> M0 必须第一天就验证单文件发布，因为 **AOT 会限制库的选择**（JSON、UI 框架），
> 等到 M2 才发现某个依赖不支持 AOT，返工成本很高。

**验收标准（M1）：**

- 迁移 10 GB / 5 万文件目录，源与目标逐文件大小+时间戳一致；
- 拔电/杀进程测试：在每个状态下强杀，重启后 `doctor` 都能给出正确判定与一键恢复；
- 回滚后源目录**逐字节**与迁移前一致（用哈希基准比对）；
- 全程**不需要管理员权限**；
- 产物是**一个 exe**（无 dll / pdb / 运行库），在**未装 .NET 的干净机器**上双击可用，且不闪黑框。

## 12. 迁移对象分级（白名单思路）

### ✅ 安全（收益大、风险小）

包管理器与构建缓存、IDE 缓存与索引、游戏安装目录（优先用平台自带库迁移）、
聊天/办公软件的文件缓存、浏览器 Cache / Code Cache / GPUCache、虚拟机镜像
（Docker/WSL/Hyper-V，**必须先停服务**）、设计软件的媒体缓存与代理文件。

### ⚠️ 谨慎（需停程序 / 有兼容风险）

完整浏览器 `User Data`（配置里有绝对路径与单实例锁）、
`AppData\Local\Packages`（UWP/AppContainer 对 Junction 偶有兼容问题）、
OneDrive/同步盘根目录（同步引擎可能不跟随）、
服务账户使用的目录（ACL 与提权风险）、
含常驻数据库的目录（先停服务）、
被备份软件覆盖的目录。

### ⛔ 别碰

`C:\Windows`、`WinSxS`、`System32`、驱动目录、
`C:\Users\<me>` **本身**、`AppData\Roaming` **整体**、`ProgramData` **整体**、
`Program Files*`（用安装器改路径，别 Junction）、
页面文件 / 休眠文件 / 系统还原点 / `System Volume Information` / `$Recycle.Bin`、
`WindowsApps`（受 ACL 与签名保护）、EFS 加密目录。

> 另外：`桌面 / 文档 / 下载 / 图片 / 视频 / 音乐` 请优先用系统的
> **右键 → 属性 → 位置 → 移动**，这是微软官方机制，比 Junction 更稳。

## 附录 B：风险登记册

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 目标盘离线导致程序异常 | 中 | 高 | 使用须知 + 开机自检 + 只允许固定盘 |
| 盘符变化导致链接全断 | 低 | 高 | Volume GUID 选项 + `doctor` 批量修复 |
| 同步软件不跟随 Junction | 中 | 中 | 预检识别并强警告 |
| 程序重建目录造成数据分裂 | 中 | 高 | 占用检测 + 空窗期极短 + `doctor` 检测 |
| 校验漏检导致静默损坏 | 低 | 高 | 默认 L2 抽样，关键目录建议 L3 |
| 高权限目录指向低权限位置（提权） | 低 | 极高 | ACL 预检，拒绝此类迁移 |
| 误删用户同名 `.bak` 目录 | 低 | 高 | owner 标记文件 + 二次确认 |
| 备份未清理导致"以为省了空间" | 中 | 低 | UI 明确显示"待释放"，`list` 汇总 |
| 单文件 exe 被 AV / SmartScreen 拦截 | 中 | 中 | 用 NativeAOT 避免自解压、代码签名、写明误报处理方式 |
| exe 放 U 盘 / 路径含中文 / 只读介质 | 低 | 低 | 状态目录回落 `%LOCALAPPDATA%`、全程 `\\?\` 规范化、无写 exe 目录的默认行为 |
| exe 被移动导致右键菜单失效 | 中 | 低 | 启动时校验注册表里记录的路径，失效则提示 `shell install` 重装 |
